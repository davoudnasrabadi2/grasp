Why now

git blame answers a question nobody is asking anymore

Tools that measure knowledge distribution and bus factor already exist — but they all rest on an old assumption: whoever wrote the code understands it. That assumption just broke. A developer whose name sits on a 2,000-line commit may have written a prompt, watched the tests go green, and merged.

# What git blame tells you
a3f9c2e maya — Rewrite cart normalization pipeline
2,340 lines changed · approved in 4 minutes · 0 review comments
 
# What the commit actually contains
Co-Authored-By: Claude <claude@anthropic.com>
Generated-with: agent · 91% of diff machine-written
 
blame shows who pressed the button — not who understands the code.

Understanding is now a hidden, decaying asset

Three things changed at once:

  • Agents write a large share of diffs — authorship no longer implies comprehension.
  • Review is becoming a rubber stamp — big PRs get approved in minutes, so the reviewer learns nothing either.
  • Agent rewrites silently erase what people knew — the version your teammate understood no longer exists.

The result is understanding debt: live, green, deployed code that no human can confidently change or debug. It's invisible until the 3 a.m. incident.

How Grasp measures understanding

Passive first. Almost everything is observed, not asked.

If a tool has to keep quizzing people to work, it fails. Grasp reads the signals your workflow already produces — no surveys, no interruptions, no self-reporting.

01 ✍️

Meaningful post-agent edits

Who deliberately edited the agent's output afterwards. A hands-on, targeted change is the strongest evidence of real engagement with the code.

02 💬

Substantive reviews

Reviews with actual content, versus drive-by approvals. Comment depth and question quality reveal who is really reasoning about the change.

03 ⏱️

Review time vs. change size

One of the strongest signals: a 2,000-line PR approved in 40 seconds was almost certainly not read. Time-to-approve scaled against diff size flags rubber-stamping.

04 🔥

Incident response

Who found and fixed the bug in that area during a production incident. Nothing builds — or proves — understanding like debugging under pressure.

05 🤖

Agent-authored detection

Which changes were machine-written, inferred from commit trailers (Co-Authored-By), PR labels, branch names, and bot accounts — zero configuration.

06 🧭

Natural erosion

Time passes. People change teams, context fades. Understanding has a half-life, and Grasp decays it honestly instead of pretending last year's knowledge is current.

phase 2 🧪

Interactive review tours

After heavy agent PRs, a 3-step guided walkthrough with a prediction question — "what does this return for an empty cart?". Wrong answers cost nothing; they just explain.

phase 2 🗣️

Explain in your own words

Write one sentence about what a change does; an LLM compares it against the code's actual behavior. A cheap, honest check of mental models.

🧮

What Grasp deliberately does not count

Lines of code. Commit counts. Green checkmarks. Activity metrics measure effort, not understanding — and incentivize the wrong behavior.

The model

A number per person × module, with two properties old tools never had

Grasp estimates an understanding level for every (person, module) pair — a weighted blend of the signals above. Two mechanisms make it reflect reality:

⏳ Half-life: understanding decays with time

Someone who knew a module well a year ago knows today's version less well. Scores decay with a configurable half-life — knowledge isn't a badge, it's a memory.

🌊 Erosion: agent rewrites erase everyone's understanding

When an agent rewrites a large part of a module, everyone's understanding drops — the version they knew is gone. Coverage falls even though nobody did anything wrong.

🎯 Coverage: how many people get the current version?

Per module: how many people hold current, sufficient understanding of the version that is actually deployed. That single number drives the whole map.

👻 Orphaned: live code, zero minds

When coverage hits zero, the module is orphaned: it compiles, it ships, it serves traffic — and nobody can confidently debug it. Orphaned × business-critical × incident history = your risk queue.

The red line

This must never become a surveillance tool

This is the biggest product risk, so it's baked into the architecture from day one — not just the marketing copy. If engineers believe their "understanding score" feeds performance reviews, teams will revolt and game the signals (hello, slow-motion approving). So:

🔒

Individual data is visible only to the individual

Your per-module understanding scores are yours. Nobody else can see them — not your lead, not HR, not in any export.

📊

Managers see aggregates, at module level

"Payments is orphaned." "Ledger is down to one person." Coverage, trends, and risk — never individual scores, never rankings.

🛡️

Trust is the go-to-market

The constraint is a selling point: teams accept the tool because it can't be used against them. Signals stay honest precisely because nobody is graded.

A manager sees "Payments is orphaned" — never "Maya doesn't understand Payments."

Step zero — before building anything

Run the validation script on a real repo. Then ask one question.

The whole thesis rests on one measurable signal: large PRs approved suspiciously fast. This repo ships a script that measures exactly that on any GitHub repository — including active open-source repos that use agents heavily.

# measure the signal on any repo (uses GITHUB_TOKEN or your `gh` login)
npx @davoudnsr/grasp-cli validate owner/repo --since=2026-04-01 --min-lines=800 --max-minutes=60

# then map who understands what, and open the dashboard on your own data
npx @davoudnsr/grasp-cli analyze owner/repo --open

# what you get:
# · what % of recently merged lines landed via big, fast-approved PRs
# · what share of merges show agent markers (trailers, branches, bot accounts)
# · the top offenders table — PR number, size, minutes-to-approve

Then show the number to a few engineering leaders and ask: "Does this number worry you?"

Their reaction is worth more than any market analysis. If the number makes them think, the problem is real.

FAQ

The questions you're already thinking

Isn't this just surveillance with extra steps?
No — and that's enforced, not promised. Individual scores are visible only to the individual. Managers see module-level aggregates only: coverage counts, trends, orphan flags. There is no leaderboard, no per-person report to anyone, and the API physically cannot return one. If that guarantee ever breaks, the product deserves to die.
How accurate can this really be?
Honest answer: it's an estimate. Understanding isn't directly observable — but its fingerprints are (deliberate edits, substantive reviews, proportionate read time, incident debugging). Grasp combines them into a risk indicator with known limitations, and presents it as one. Teams that expect a scoreboard will be disappointed; that's intentional.
What does a team do with it — just stare at red cells?
That's the "now what" risk, and it's why phase 2 exists: guided tours for orphaned modules, on-call refreshers, pairing suggestions, merge-protection recommendations. The MVP deliberately proves demand first; the repair layer is where retention lives.
Does it need an LLM? What does it cost to run?
Most of the value — passive signals, scoring, coverage, alerts, the map — needs no LLM and runs cheap on plain event data. The LLM only enters in phase 2: generating tour steps and comparing free-form explanations against actual code behavior.
GitHub only?
The MVP is a GitHub App (webhooks for PRs, reviews, commits). GitLab, incident-tool integrations (PagerDuty, Opsgenie) and CI signals are on the roadmap — the engine is source-agnostic by design.
What about gaming — people slow-walking approvals?
Individual scores aren't visible to managers, so there's no incentive to fake them. And Grasp's "deliberately not counted" list — lines written, commit counts, activity volume — removes the usual vanity metrics that reward noise over comprehension.
